# Проектные решения безопасности

### D-01. Серверная проверка аутентификации и разрешенных операций

**Контекст:** API-клиент считается недоверенной стороной и может отправлять произвольные запросы к серверу. Сам факт успешной аутентификации не означает, что пользователь имеет право выполнять любую операцию. Сервер должен отдельно проверять, разрешено ли запрошенное действие для роли текущего пользователя.

**Решение:** Перед выполнением защищённой операции сервер проверяет аутентификацию пользователя, а затем проверяет, разрешено ли его роли выполнять это действие. Если пользователь не аутентифицирован или его роль не имеет доступа к операции, сервер отклоняет запрос и не изменяет данные.

**Обоснование:** Такое разделение проверок позволяет не только закрыть доступ неавторизованным пользователям, но и не допустить выполнение операций пользователями с неподходящей ролью. Это защищает функции администратора и учителя от использования другими ролями и не позволяет изменить состояние системы через прямой API-запрос.

**Связанные угрозы:** T-01, T-06, T-07

**Связанные требования:** SR-01, SR-06, SR-07

**Будущая проверка:**

- **Условие:** в системе есть пользователи с ролями Ученика, Учителя и Системного администратора.
- **Действие:** отправить запрос к защищённой операции сначала без аутентификации, затем от имени пользователя, чья роль не имеет права выполнять эту операцию.
- **Ожидаемый результат:** сервер отклоняет оба запроса и не изменяет данные системы. При выполнении запроса пользователем с подходящей ролью операция выполняется успешно.

**Ограничения и последствия:** Проверка должна выполняться на сервере для каждой защищённой операции. Если для новой операции забыть добавить проверку авторизации, пользователь может получить доступ к действию, которое не предусмотрено его ролью. Поэтому при добавлении новых API-операций необходимо отдельно указывать, каким ролям они доступны.

### D-02. Проверка ограничений при выдаче устройства

**Контекст:** Ученик может одновременно иметь не более двух устройств, причём устройства должны быть разных типов. Даже если каждая заявка по отдельности выглядит допустимой, при последовательном или одновременном одобрении нескольких заявок это ограничение может быть нарушено.

**Решение:** При одобрении заявки сервер повторно проверяет, сколько устройств уже выдано ученику и какие у них типы. Если после выдачи у ученика окажется больше двух устройств или у ученика уже есть устройство такого же типа, заявка не одобряется и состояние системы не изменяется.

**Обоснование:** Проверка ограничения именно при одобрении заявки позволяет учитывать текущее состояние системы на момент выдачи устройства. Это не даёт одобрить заявку, если после её выполнения ученик получит больше двух устройств или два устройства одного типа.

**Связанные угрозы:** T-08

**Связанные требования:** SR-08

**Будущая проверка:**

- **Условие:** у ученика уже есть два выданных устройства разных типов либо одно устройство определённого типа.
- **Действие:** попытаться одобрить заявку на третье устройство или на устройство того же типа, которое уже есть у ученика.
- **Ожидаемый результат:** сервер отклоняет одобрение заявки, количество и состав выданных ученику устройств не изменяются.

**Ограничения и последствия:** Проверка должна выполняться при каждом одобрении заявки, а не только при её создании. При изменении правил выдачи оборудования эту проверку тоже потребуется изменить.

### D-03. Ограничение доступа ученика к чужим заявкам

**Контекст:** Ученик должен иметь доступ только к своим заявкам. Если сервер неправильно ограничивает выборку, ученик может получить данные заявок других учеников через обычный разрешённый запрос.

**Решение:** При запросе списка своих заявок сервер возвращает только те заявки, которые принадлежат текущему аутентифицированному ученику. Идентификатор ученика для выборки не берётся из параметров запроса, а определяется сервером после аутентификации пользователя.

**Обоснование:** Такое ограничение не позволяет ученику получить доступ к заявкам других пользователей даже при прямом обращении к API. Сервер сам определяет, какие заявки относятся к текущему ученику, и возвращает только их.

**Связанные угрозы:** T-09

**Связанные требования:** SR-09

**Будущая проверка:**

- **Условие:** в системе есть два ученика, у каждого из которых есть свои заявки.
- **Действие:** выполнить запрос на просмотр своих заявок от имени одного из учеников.
- **Ожидаемый результат:** сервер возвращает только заявки этого ученика; заявки другого ученика в ответ не попадают.

**Ограничения и последствия:** Ограничение должно применяться ко всем операциям просмотра заявок ученика. Если появятся новые способы получения списка заявок, в них также необходимо учитывать текущего пользователя и не допускать доступ к чужим заявкам.
