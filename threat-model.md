# Модель угроз

## 1. Контекст продукта

Проект «Школьная система инвентаризации» предназначен для учёта технического оборудования школьного IT-полигона и управления его выдачей ученикам.

В системе предусмотрены три роли:
- **Системный администратор** - управляет учётными записями учеников и учителей, добавляет устройства и изменяет информацию и статус устройств;
- **Учитель** — просматривает заявки учеников, одобряет или отклоняет их, подтверждает возврат оборудования;
- **Ученик** — просматривает доступное оборудование, создаёт заявки на получение оборудования и просматривает состояние собственных заявок

Основные сценарии продукта:
1. получение оборудования учеником;
2. возврат устройства;
3. добавление нового устройства системным администратором

Для выдачи оборудования действует предметное ограничение:
- у ученика одновременно может находиться не более двух устройств;
- находящиеся у одного ученика устройства должны быть разных типов

Для модели используются требования безопасности из `security-requirements.md`:
- `SR-01` — доступ к функционалу проекта предоставляется только авторизованным пользователям;
- `SR-02` — действия авторизованных пользователей должны записываться в журнал аудита;
- `SR-03` — система должна сохранять события при выдаче и возвращении устройств;
- `SR-04` — система должна работать только по защищённым каналам передачи;
- `SR-05` — только системный администратор может добавлять и удалять аккаунты учеников и учителей;
- `SR-06` — только системный администратор может редактировать список устройств;
- `SR-07` — только учитель может рецензировать заявки;
- `SR-08` — ученик может иметь только два устройства уникального типа;
- `SR-09` — ученик может просматривать исключительно свои заявки

## 2. Основные объекты и свойства

### Устройства

**Значимы:**
- идентификатор;
- тип устройства;
- информация об устройстве;
- статус;
- текущий владелец

**Важные свойства:**
- целостность данных устройства;
- согласованность статуса и фактического владельца;
- изменение данных и статуса только пользователем с необходимыми полномочиями

Несанкционированное изменение может привести к ошибочной выдаче оборудования, неверному определению владельца или некорректному состоянию системы.

### Заявки

**Значимы:**
- идентификатор заявки;
- владелец заявки;
- выбранное устройство;
- состояние заявки;
- решение Учителя

**Важные свойства:**
- целостность;
- конфиденциальность;
- правильность владельца;
- изменение состояния только разрешённой ролью

Ученик должен иметь доступ только к собственным заявкам, а решение об одобрении или отклонении заявки может принимать только Учитель.

### Пользователи и роли

**Значимы:**
- учётная запись пользователя;
- его роль;
- наличие пользователя в системе

**Важные свойства:**
- подлинность пользователя;
- целостность учётных данных;
- соблюдение полномочий роли

Только Системный администратор может добавлять и удалять аккаунты учеников и учителей и изменять список устройств. Полномочия одной роли не должны подменяться полномочиями другой.

### Состояние выданного оборудования

**Система должна сохранять следующий предметный инвариант:**
- у одного ученика одновременно находится не более двух устройств;
- эти устройства должны быть разных типов

Нарушение этого свойства приводит к некорректному состоянию системы и нарушению правил выдачи оборудования.

### Журнал аудита

**Журнал используется для установления:**
- кто выполнил действие;
- какое действие было выполнено;
- над каким объектом;
- когда оно было выполнено;
- каков результат операции

**Важные свойства:**
- целостность;
- сохранность;
- подотчётность действий

События выдачи и возврата устройств не должны теряться при временной недоступности внешнего сервиса журналирования.

### Данные и команды API

Через API передаются идентификаторы, данные заявок, решения Учителя, сведения об устройствах и пользователях.
**Важные свойства:**
- конфиденциальность при передаче;
- целостность при передаче;
- выполнение защищённых операций только авторизованными пользователями

## 4. Граница доверия 

### Граница 1. API-клиент → сервер приложения

Клиентская сторона считается недоверенной.

**Через эту границу проходят:**
- идентификаторы устройств;
- идентификаторы заявок;
- идентификаторы пользователей;
- данные заявок;
- статусы и данные устройств;
- решения по заявкам;
- команды управления пользователями

**Сервер не должен автоматически считать действие разрешённым только потому, что запрос:**
- синтаксически корректен;
- содержит существующий идентификатор;
- отправлен аутентифицированным пользователем

**Сервер самостоятельно должен определить:**
- кто выполняет действие;
- какая у пользователя роль;
- разрешено ли действие этой роли;
- допустимо ли действие для текущего состояния объекта;
- сохраняет ли операция предметные ограничения системы

### Граница 2. Сервер приложения → Apache Kafka

Сервер не может автоматически считать событие аудита сохранённым только потому, что была предпринята попытка отправки сообщения.
При недоступности Kafka событие должно быть сохранено локально.

## 6. Точки входа 
**Для анализа используются следующие логические операции:**

`POST /auth/login` - аутентификация пользователя 

`GET /devices` - просмотр списка устройств

`POST /requests` - создание заявки Учеником 

`GET /requests/my` - просмотр Учеником своих заявок

`PATCH /requests/{requestId}/review` - рецензирование заявки Учителем 

`PATCH /devices/{deviceId}/return` - подтверждение возврата устройства Учителем 

`POST /users` - добавление Ученика или Учителя Администратором 

`DELETE /users/{userId}` - удаление Ученика или Учителя 

`POST /devices` - добавление нового устройства 

`PATCH /devices/{deviceId}` - изменение данных или статуса устройства 

### Обработка основных операций

| Операция | Входные данные | Роль | Что может измениться | Что должен проверить сервер |
| --- | --- | --- | --- | --- |
| Аутентификация | учётные данные пользователя | любая | состояние сессии / контекст аутентификации | корректность учётных данных и существование пользователя |
| Просмотр списка устройств | параметры запроса списка | Ученик, Учитель, Системный администратор | состояние системы не изменяется | пользователь авторизован и имеет право просматривать список |
| Создание заявки | идентификатор устройства | Ученик | создаётся новая заявка | пользователь имеет роль Ученика; устройство существует и доступно; заявка не нарушает ограничение `SR-08` |
| Просмотр собственных заявок | идентификатор заявки или запрос списка заявок | Ученик | состояние системы не изменяется | заявка принадлежит текущему Ученику |
| Рецензирование заявки | идентификатор заявки, решение `approve/reject` | Учитель | изменяется статус заявки; при одобрении может измениться состояние и владелец устройства | пользователь имеет роль Учителя; заявка существует; операция допустима для текущего состояния; выдача не нарушает `SR-08` |
| Подтверждение возврата | идентификатор заявки или устройства | Учитель | устройство освобождается, изменяется его статус и информация о владельце | пользователь имеет роль Учителя; устройство действительно выдано соответствующему ученику |
| Добавление пользователя | данные пользователя, роль | Системный администратор | создаётся новая учётная запись | пользователь имеет роль Системного администратора; входные данные допустимы |
| Удаление пользователя | идентификатор пользователя | Системный администратор | учётная запись удаляется | пользователь имеет роль Системного администратора; удаляемый пользователь существует |
| Добавление устройства | данные устройства | Системный администратор | создаётся запись устройства | пользователь имеет роль Системного администратора; данные устройства допустимы |
| Изменение устройства | идентификатор устройства, новые данные или статус | Системный администратор | изменяются данные или статус устройства | пользователь имеет роль Системного администратора; устройство существует; новое состояние допустимо |

## 7. Пример входных данных

**Аутентификация:**
```json
{
  "login": "student01",
  "password": "password"
}
```

**Создание заявки:**
```json
{
  "deviceId": "device-17"
}
```

**Рецензирование заявки:**

```json
{
  "decision": "approved"
}
```

Возможные значения `decision`:
```text
approved
rejected
```

**Добавление пользователя:**
```json
{
  "name": "Иван Иванов",
  "login": "ivanov",
  "role": "student"
}
```

Возможные значения `role`:
```text
student
teacher
```

**Добавление устройства:**
```json
{
  "name": "MacBook Air",
  "type": "laptop",
  "status": "available"
}
```

**Изменение устройства:**
```json
{
  "status": "maintenance"
}
```

## 8. Что считать недоверенным вводом 
**К недоверенным данным относятся все параметры, поступающие от API-клиента, например:**
- `deviceId`;
- `requestId`;
- `userId`;
- данные пользователя;
- роль создаваемого пользователя;
- информация об устройстве;
- статус устройства;
- решение по заявке;
- другие параметры API-запроса

**Особенно важно различать:**
- роль текущего аутентифицированного пользователя
- роль пользователя, которого администратор создаёт в системе
Полномочия текущего пользователя сервер не должен определять только из обычного параметра запроса

Корректный формат значения не означает, что действие допустимо.
